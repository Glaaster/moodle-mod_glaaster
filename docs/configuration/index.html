Fichiers de configuration​

version.php​

mod/glaaster/version.php

Configuration de la version du plugin et dépendances Moodle.

$plugin->version = 2026091502;                    // Format YYYYMMDDXX (réécrit par semantic-release)
$plugin->requires = 2022041200;                   // Plancher technique hérité
$plugin->component = 'mod_glaaster';
$plugin->release = '5.3.2';                       // Réécrit par semantic-release (5.3.3 au prochain tag)
$plugin->maturity = MATURITY_STABLE;
$plugin->supported = [405, 502];                  // Moodle 4.5 → 5.2
$plugin->cron = 0;
$plugin->dependencies = ['mod_lti' => ANY_VERSION]; // Classes OAuth déléguées à mod_lti

Paramètres clés :

  • version / release : mis à jour par scripts/bump-version.sh (job semantic-release) — YYYYMMDD + patch sur 2 chiffres
  • supported : Moodle 4.5 à 5.2 ; PHP 8.1–8.3 (4.5–5.1), PHP 8.3+ requis pour 5.2 (8.4 supporté)
  • dependencies : mod_lti doit être installé (OAuth délégué depuis 5.0)

Rôle Glaaster API (db/install.php)​

mod_glaaster_create_api_role() crée à l'installation (et ré-applique à l'upgrade) le rôle glaasterapi, assignable en contexte système uniquement, destiné à l'utilisateur du token du Document Service. Capacités accordées par mod_glaaster_assign_api_role_capabilities() :

CapacitéUsage
moodle/course:viewVoir les cours sans inscription
moodle/course:updateRequis par core_course_get_contents
moodle/course:viewhiddencoursesRessources dans des cours cachés
moodle/course:viewhiddensectionsRessources dans des sections cachées
moodle/course:viewhiddenactivitiesActivités ressource cachées
moodle/course:ignoreavailabilityrestrictionsActivités avec restrictions d'accès (5.2.1+)
mod/resource:viewRessources fichier
mod/folder:viewContenu des dossiers
webservice/rest:useProtocole REST
moodle/cohort:viewCohortes des autres utilisateurs via get_user_cohorts (5.3.4+)
  • assign_capability() est appelé avec $overwrite = true : une de ces capacités mise à Prevent/Prohibit à la main repasse à Allow après upgrade.
  • moodle/cohort:view est accordée automatiquement depuis 5.3.4 (étape d'upgrade 2026100100) ; en 5.3.3 elle devait être ajoutée à la main.

Cours conteneur « Glaaster » (auto-provisionné)​

À la connexion d'un type d'outil (enregistrement dynamique, glaaster_add_type()), glaaster_provision_hidden_instance() crée l'unique instance Glaaster du site : catégorie + cours Glaaster (idnumber glaaster_hidden_container) + module, tous visibles (5.2+). glaaster_grant_container_course_access() accorde moodle/course:view et mod/glaaster:view au rôle d'archétype user dans ce seul cours (lancement sans inscription). Idempotent ; un échec ne bloque pas l'enregistrement LTI. Des étapes d'upgrade provisionnent / rendent visible le conteneur sur les sites existants.

mod_glaaster_get_user_cohorts (5.3.3+)​

'mod_glaaster_get_user_cohorts' => [
    'classname'     => 'mod_glaaster\external\get_user_cohorts',
    'methodname'    => 'execute',
    'type'          => 'read',
    'capabilities'  => 'moodle/cohort:view',
    'loginrequired' => true,
    // Pas de 'ajax' => true : appel uniquement via token REST (Document Service)
],
  • Un utilisateur peut lire ses propres cohortes sans capacité particulière.
  • Lire les cohortes d'un autre userid exige moodle/cohort:view en contexte système (correction IDOR, issue #21).
  • Le compte du token Glaaster API (glaaster_api) doit donc avoir moodle/cohort:view : accordée par le rôle glaasterapi depuis 5.3.4.

Service pré-configuré glaaster_api​

Service externe Glaaster API créé automatiquement à l'install/upgrade (enabled = 1, restrictedusers = 1, downloadfiles = 1). Moodle interdit d'en modifier la liste de fonctions depuis l'UI :

  • mod_resource_get_resources_by_courses
  • core_files_get_files
  • core_course_get_contents
  • core_group_get_course_user_groups
  • mod_glaaster_get_user_cohorts

glaaster_check_webservice_configured() considère le service configuré s'il est actif et possède au moins un token non expiré.

Enregistrement (méthode recommandée)​

  1. Créer un utilisateur dédié (ex. glaasterapi), lui attribuer le rôle Glaaster API (contexte système) ; le choisir dans la carte API
  2. Générer le token API (service glaaster_api)
  3. Cliquer Connect → enregistrement dynamique LTI 1.3 (URLs, JWKS, scopes récupérés automatiquement)
  4. À la connexion, le cours conteneur « Glaaster » est provisionné → icônes actives

En cas de problème, la page renvoie vers la FAQ https://support.glaaster.com et support@glaaster.com (5.1.1+).

Mode d'ouverture (launchcontainer)​

Constantes dans locallib.php, options de glaaster_get_launch_container_options() :

ConstanteValeurOption (lang)
MOD_GLAASTER_LAUNCH_CONTAINER_EMBED2Embed (iframe, blocs conservés)
MOD_GLAASTER_LAUNCH_CONTAINER_EMBED_NO_BLOCKS3Embed, without blocks
MOD_GLAASTER_LAUNCH_CONTAINER_REPLACE_MOODLE_WINDOW5Existing window (pleine page)
MOD_GLAASTER_LAUNCH_CONTAINER_WINDOW4New window (nouvel onglet) — défaut depuis 5.3.2
  • glaaster_get_default_launch_container() : valeur absente/invalide → WINDOW (idem garde d'écriture de toolconfigure.php et valeur semée par registration_helper).
  • Le réglage site prime sur la valeur du type d'outil et de l'activité (toujours DEFAULT = 1) — contrairement à mod_lti.
  • Mobile / tablette : toujours REPLACE_MOODLE_WINDOW, quel que soit le réglage.
  • L'enregistrement appelle rebuild_course_cache(0, true) (le mode est figé dans cached_cm_info par glaaster_get_coursemodule_info()).
  • En mode nouvel onglet, les boutons contextuels ont target="_blank" + rel="noopener" et l'URL porte forceview=1 (redirection directe vers le lancement). Jamais sur mobile/tablette (5.3.4) : sinon view.php sautait la redirection et affichait l'iframe intégrée.

Services LTI Advantage​

Sous-plugins service/ conservés : memberships (NRPS, https://purl.imsglobal.org/spec/lti-nrps/scope/contextmembership.readonly), toolsettings, profile, toolproxy.

Synchronisation des notes supprimée : table glaaster_submission et sous-plugins basicoutcomes / gradebookservices retirés (db/upgrade.php). Aucun réglage de notes (« Accept grades », AGS) n'est plus proposé.

Paramètres de sécurité​

JWT​

Algorithme : RS256 (RSA-SHA256) Durée de vie : 60 s (exp = iat + 60, glaaster_sign_jwt()) JWKS plateforme : /mod/glaaster/certs.php

Tokens OAuth2​

Durée de vie : 3600 s (MOD_GLAASTER_ACCESS_TOKEN_LIFE) Stockage : Table {glaaster_access_tokens} Nettoyage : Tâche planifiée clean_access_tokens (quotidienne)

Points d'entrée sans authentification​

mod_glaaster_validate_instance et mod_glaaster_check_tool_status sont loginrequired = false : ils ne renvoient qu'un booléen (isvalid / active) et ne modifient aucune donnée.

  • Les fetchs JWKS sortants passent par le helper curl Moodle (curlsecurityblockedhosts).

Dépannage​

Après modification du code​

  1. Upgrade Moodle (enregistre web services, rôle Glaaster API, conteneur) :

    php admin/cli/upgrade.php

  2. Purge des caches :

    php admin/cli/purge_caches.php

  3. Hard refresh navigateur : Ctrl+Shift+R

Cohortes : required_capability_exception​

Depuis 5.3.3, mod_glaaster_get_user_cohorts exige moodle/cohort:view pour lire les cohortes d'un autre utilisateur. Depuis 5.3.4, le rôle Glaaster API la reçoit automatiquement à l'upgrade.

Solution : mettre à jour en 5.3.4+ (php admin/cli/upgrade.php). Sinon, ou si le token utilise un autre rôle : Site administration → Users → Permissions → Define roles → rôle de l'utilisateur du token Glaaster API → autoriser moodle/cohort:view (contexte système), puis php admin/cli/upgrade.php et php admin/cli/purge_caches.php.

Boutons absents ou désactivés (grisés, badge « ? »)​

Causes possibles :

  • Aucune icône : « Enable contextual icons » décoché (iconsenabled = 0)
  • Icônes désactivées : aucune instance valide — cours conteneur non provisionné (outil pas encore connecté, ou site passé directement en 5.1.0 → mettre à jour ≥ 5.1.1), tooldomain ne correspondant pas au type d'outil, ou instance en suppression (deletioninprogress = 1)
  • Extension de fichier non supportée
  • Erreur JavaScript (vérifier console navigateur)
  • Webservices désactivés ou token glaaster_api absent/expiré (seul le watcher de suppression temps réel est alors indisponible)

Solution :

# Vérifier / activer les webservices
php admin/cli/cfg.php --name=enablewebservices
php admin/cli/cfg.php --name=enablewebservices --set=1

# Vérifier le réglage des icônes
php admin/cli/cfg.php --component=mod_glaaster --name=iconsenabled

Activités bloquées en deletioninprogress = 1​

Avant 5.3.1, la suppression d'une activité liée à un type d'outil site échouait (TypeError PHP 8 dans le backup de la corbeille). Le correctif n'agit pas rétroactivement :

SELECT cm.id, cm.course, cm.instance
FROM {course_modules} cm
JOIN {modules} m ON m.id = cm.module
WHERE m.name = 'glaaster' AND cm.deletioninprogress = 1;

Remettre deletioninprogress à 0 sur ces lignes, puis relancer la suppression depuis le cours.

Le mode d'ouverture ne change pas​

Le mode est figé dans cached_cm_info. L'enregistrement depuis la page admin reconstruit les caches de cours ; après un changement par upgrade (ex. défaut → nouvel onglet en 5.3.2) ou via CLI, lancer php admin/cli/purge_caches.php. Pour conserver l'intégration, choisir explicitement Embed, without blocks. Sur mobile/tablette, l'ouverture est toujours en fenêtre existante.

Documents manquants côté Glaaster​

Ressources dans un cours/section/activité cachés ou derrière une restriction d'accès : vérifier que le rôle Glaaster API a bien les capacités viewhidden* et moodle/course:ignoreavailabilityrestrictions (ré-appliquées par php admin/cli/upgrade.php).

JWT launch échoue​

Causes possibles :

  • JWKS endpoint non accessible
  • Signature invalide (clés différentes)
  • JWT expiré (exp = 60 s après iat)
  • JWKS outil injoignable ou invalide → errorkeysetdownloadfailed (5.0+)

Solution :

  • Vérifier accessibilité de /mod/glaaster/certs.php (JWKS plateforme)
  • Comparer iss JWT avec URL Moodle
  • Vérifier horloge serveur (synchronisation NTP)
