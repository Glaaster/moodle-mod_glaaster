Release Notes — v5.3.0

Changes since v5.2.1

Minor release. One feature, no database schema changes, no breaking changes.

The LTI launch now carries three extra claims to the Glaaster tool: an optional redirect target, the activity cmid, and the plugin's own version.

✨ Features​

Redirect target forwarded to the tool​

A launch can now request that Glaaster open on a specific front-end route, by adding a redirect parameter to the activity URL:

/mod/glaaster/view.php?id={cmid}&redirect={target}

The value is read in view.php with PARAM_ALPHANUMEXT and forwarded, unchanged, through the whole launch chain:

StepFileWhat carries the value
1. Viewview.phpredirect query parameter → launch.php params
2. Launchlaunch.phpoptional_param('redirect', '', PARAM_ALPHANUMEXT)
3. Login requestlocallib.php — glaaster_build_login_request()lti_message_hint payload
4. Auth callbackauth.phpread back from $ltimessagehint->redirect
5. Request buildlocallib.php — glaaster_build_request()redirect request parameter
6. JWTlocallib.php — glaaster_sign_jwt()redirect claim

The token is opaque to the plugin: it is passed through as-is and never resolved or validated against a list of routes. The allow list lives on the tool side, which is the component that knows its own routes. PARAM_ALPHANUMEXT restricts the value to letters, digits, hyphens and underscores, so no path or URL can be smuggled through it.

Every step is guarded by !empty(): when no redirect is requested, the claim is absent from the JWT rather than sent as an empty string.

Both launch paths are covered — the embedded-without-blocks branch in view.php and the default branch that builds $launchurl.

Activity cmid sent as its own claim​

The standard resource_link_id claim carries the Glaaster instance id, not the course module id. A tool receiving only resource_link_id cannot address the activity in Moodle, because the cmid is not derivable from the instance id without a database lookup.

glaaster_build_request() now sends activity_cmid alongside it, and glaaster_sign_jwt() promotes it to a top-level JWT claim.

Plugin version reported in the launch​

The standard tool_platform.version / tool_consumer_info_version claim carries the Moodle core version, so the tool had no way to know which build of this plugin produced a launch — which makes debugging a launch against an unknown plugin build guesswork.

Two claims are now added:

ClaimSourceExample
plugin_releasecore_plugin_manager::instance()->get_plugin_info('mod_glaaster')->release5.3.0
plugin_versionget_config('mod_glaaster', 'version'), cast to string2026091400

The release string only exists in version.php, which the plugin manager reads for us; only the numeric version is stored in config, hence the two different sources. Both are guarded by !empty().

✅ Tests​

externallib_test.php was updated for the new claims:

  • Expected parameter count raised from 34 to 37 (activity_cmid, plugin_release, plugin_version).
  • New assertions check plugin_release against the plugin manager, plugin_version against config, and activity_cmid against $lti->cmid.
  • A negative assertion checks that redirect is absent from the launch data when no redirect was requested.

Upgrade Notes​

Standard plugin upgrade — no manual intervention required, no schema change.

php admin/cli/upgrade.php
php admin/cli/purge_caches.php

The cache purge matters here: glaaster_get_coursemodule_info() results are cached, and the launch URLs built from them change shape once the plugin starts forwarding redirect.

Tool-side requirement: the redirect claim is only useful if the Glaaster tool maps the token to a route. Until it does, sending ?redirect=… is harmless — the claim is simply ignored.

All new claims are additive. Existing launches that send no redirect produce the same JWT as 5.2.1 plus activity_cmid, plugin_release and plugin_version. A tool that validates the claim set strictly (rejecting unknown claims) would need updating; a tool that ignores unknown claims needs no change.
